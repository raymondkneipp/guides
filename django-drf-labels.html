Django + DRF — Applications & Labels

A small REST API: authenticated users create Applications, each with many Labels. Label names are globally unique, admins gate the is_protected flag, and labels can be created inline when you create an Application.

The rules we're implementing
  1. Users can create an Application; an Application has many Labels (M2M).
  2. A Label has a unique name and an is_protected boolean.
  3. Only admins can set is_protected = true, or update a label that's already protected.
  4. When creating an Application you can supply labels inline to create alongside it.
  5. Label names are unique — if a supplied name already exists, reuse the existing label (don't error, don't overwrite it).

In DRF, an admin is just a user with is_staff=True (what you get from createsuperuser, or tick "staff status" in the Django admin). We use request.user.is_staff as the admin check throughout.

2. Models

labels/models.py

from django.conf import settings
from django.db import models


class Label(models.Model):
    name = models.CharField(max_length=100, unique=True)      # globally unique
    is_protected = models.BooleanField(default=False)

    def __str__(self):
        return self.name


class Application(models.Model):
    name = models.CharField(max_length=200)
    owner = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="applications",
    )
    labels = models.ManyToManyField(Label, related_name="applications", blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.name
Why M2M + unique name: labels are shared, first-class rows (not owned by one app), so "add the urgent label to five apps" reuses one Label row. The unique constraint is what makes "reuse if it exists" meaningful.

3. Serializers

Two jobs: (a) the Label serializer enforces "only admins can protect," and (b) the Application serializer accepts inline labels and does the get-or-create.

labels/serializers.py

from django.db import transaction
from rest_framework import serializers

from .models import Application, Label


class LabelSerializer(serializers.ModelSerializer):
    class Meta:
        model = Label
        fields = ["id", "name", "is_protected"]

    def validate_is_protected(self, value):
        # Rule 3a: only admins can flip is_protected on.
        request = self.context.get("request")
        if value and not (request and request.user.is_staff):
            raise serializers.ValidationError("Only admins can protect a label.")
        return value


class LabelInputSerializer(serializers.Serializer):
    # Shape of each label supplied inline on Application create.
    name = serializers.CharField(max_length=100)
    is_protected = serializers.BooleanField(required=False, default=False)


class ApplicationSerializer(serializers.ModelSerializer):
    labels = LabelSerializer(many=True, read_only=True)                       # output
    labels_input = LabelInputSerializer(many=True, write_only=True, required=False)  # input

    class Meta:
        model = Application
        fields = ["id", "name", "owner", "labels", "labels_input", "created_at"]
        read_only_fields = ["owner", "created_at"]

    def create(self, validated_data):
        labels_data = validated_data.pop("labels_input", [])
        request = self.context["request"]
        is_admin = request.user.is_staff

        with transaction.atomic():
            application = Application.objects.create(
                owner=request.user, **validated_data
            )

            for item in labels_data:
                name = item["name"]
                wants_protected = item.get("is_protected", False)

                # Rule 3a: non-admins can't create a protected label.
                if wants_protected and not is_admin:
                    raise serializers.ValidationError(
                        {"labels_input": f"Only admins can create the protected label '{name}'."}
                    )

                # Rule 5: unique names -> reuse if it exists, else create.
                # is_protected in `defaults` only applies when a NEW row is created
                # (and only admins reach here with it True), so existing labels
                # are used as-is and never mutated.
                label, _created = Label.objects.get_or_create(
                    name=name,
                    defaults={"is_protected": bool(wants_protected)},
                )
                application.labels.add(label)

        return application
The key move is get_or_create(name=..., defaults={...}). If the name exists it returns that row and ignores defaults — so you "just use the one that exists" for free, and you can never flip an existing label's protection through the Application endpoint (that's an admin-only Label update, below). Wrapping in transaction.atomic() means a rejected protected-label doesn't leave a half-created Application behind.

4. Permission: don't touch protected labels

Rule 3b — a label that's already protected can only be updated/deleted by an admin. That's an object-level permission on the Label endpoint.

labels/permissions.py

from rest_framework import permissions


class ProtectedLabelPermission(permissions.BasePermission):
    """Only admins may modify a label that is protected."""

    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:   # GET/HEAD/OPTIONS
            return True
        if obj.is_protected and not request.user.is_staff:
            return False
        return True
This handles updating a protected label. Trying to set is_protected=true in the first place is already blocked by validate_is_protected in the serializer. Together they cover both halves of Rule 3.

5. Views

labels/views.py

from rest_framework import permissions, viewsets

from .models import Application, Label
from .permissions import ProtectedLabelPermission
from .serializers import ApplicationSerializer, LabelSerializer


class LabelViewSet(viewsets.ModelViewSet):
    queryset = Label.objects.all()
    serializer_class = LabelSerializer
    permission_classes = [permissions.IsAuthenticated, ProtectedLabelPermission]


class ApplicationViewSet(viewsets.ModelViewSet):
    serializer_class = ApplicationSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_queryset(self):
        # Users only see their own applications.
        return (
            Application.objects
            .filter(owner=self.request.user)
            .prefetch_related("labels")
        )

7. Try it

Examples with HTTPie (:= sends raw JSON). Curl works too — just send a JSON body with Basic auth.

Create an app with two brand-new labels

http -a alice:pw POST :8000/api/applications/ \
  name="Billing Service" \
  labels_input:='[{"name": "backend"}, {"name": "urgent"}]'

Create a second app reusing "backend"

http -a alice:pw POST :8000/api/applications/ \
  name="Reports Service" \
  labels_input:='[{"name": "backend"}, {"name": "analytics"}]'
# "backend" is reused (same Label row); "analytics" is created new.

Admin protects a label directly

http -a admin:pw PATCH :8000/api/labels/1/ is_protected:=true   # 200 OK

Non-admin tries to protect → blocked

http -a alice:pw PATCH :8000/api/labels/2/ is_protected:=true
# 400 — {"is_protected": ["Only admins can protect a label."]}

http -a alice:pw PATCH :8000/api/labels/1/ name="renamed"
# 403 — label 1 is protected; only admins may modify it.

http -a alice:pw POST :8000/api/applications/ \
  name="Sneaky" labels_input:='[{"name": "vip", "is_protected": true}]'
# 400 — "Only admins can create the protected label 'vip'."

8. Edge cases & choices

  • Existing labels are never mutated here. If a non-admin references an existing (even protected) label by name on Application create, it just gets attached — attaching isn't modifying. Changing a label's protection is a separate, admin-only PATCH /api/labels/{id}/.
  • Non-admin sends is_protected:true for a name that already exists: the code above rejects it for clarity (they asked to protect). If you'd rather silently ignore it for names that already exist, look the label up first and only enforce the rule when you're about to create a new one.
  • Uniqueness race: get_or_create can still raise IntegrityError if two requests create the same new name at the same instant. The DB unique constraint keeps you correct; wrap in try/except IntegrityError and re-fetch if you want it fully race-proof.
  • Duplicate names in one request ([{"name":"x"},{"name":"x"}]) are harmless — the second get_or_create returns the row the first just made, and adding the same label to an M2M twice is a no-op.
  • Want protection immutable once set? Add a validate on LabelSerializer that blocks turning is_protected back to false unless admin, mirroring the on-switch rule.
