0 · What we're building & why

GitHub publishes a live public firehose of everything happening across the site — every push, star, fork, issue, and pull request — at https://api.github.com/events. It's real, messy, high-volume data you didn't have to invent. Perfect fuel for a search platform.

In this first project you'll poll that firehose, store each event durably in Postgres, mirror it into Elasticsearch, and expose a search API. No fake data, ever — that's a hard rule for the whole series.

GitHub Events API ┌──────────────────────────────┐ api.github.com/events ──poll──▶ │ Django (management cmd) │ │ ingest_events: fetch + save │ └───────────┬──────────────────┘ │ write (source of truth) ▼ ┌───────────────┐ │ PostgreSQL │ └───────┬───────┘ │ mirror for search ▼ GET /api/search?q=… ┌──────────────┐ query ┌───────────────┐ ──────────────────────▶│ Django + DRF │──────────▶│ Elasticsearch │ └──────────────┘ └───────────────┘ Everything runs together via one docker-compose.yml.
Why two stores Postgres is your system of record — durable, relational, the truth. Elasticsearch is a search index — it trades some durability guarantees for blazing full-text queries, ranking, and aggregations that would be painful in SQL. Mirroring Postgres → ES is a pattern you'll meet everywhere. In Project 3 the mirror stops being a direct call and becomes a Kafka pipeline — this project is where you feel why you'd want that. (Project 2 first gives the platform a UI.)
  • Django + DRF — models, migrations, serializers, viewsets, routing. The API core.
  • Postgres — the durable table of events, driven entirely by environment variables.
  • Elasticsearch — an inverted index, a mapping, bulk indexing, and query DSL.
  • Docker Compose — three services (web, db, search) wired together with one command.

3 · The GithubEvent model

Teach. A model is a Python class that maps to a database table; each attribute is a column. Django's migrations turn changes to that class into versioned SQL. We'll build the model in two passes so you see each decision — first the raw shape of a GitHub event, then the indexes that make it fast to query.

Pass 1 — the fields

Look at one real event first so the columns aren't abstract:

{
  "id": "41234567890",
  "type": "PushEvent",
  "actor": { "login": "torvalds" },
  "repo":  { "name": "torvalds/linux" },
  "payload": { "commits": [ { "message": "Merge tag ..." } ] },
  "created_at": "2026-07-08T14:03:11Z"
}

Map that straight onto a model. Start plain — no indexes yet:

events/models.py — first pass 
from django.db import models


class GithubEvent(models.Model):
    event_id = models.CharField(max_length=32, unique=True)   # GitHub's event id
    type = models.CharField(max_length=64)                    # "PushEvent", "WatchEvent", ...
    actor_login = models.CharField(max_length=255)            # who did it
    repo_name = models.CharField(max_length=255)              # "owner/repo"
    created_at = models.DateTimeField()                       # when GitHub says it happened
    payload = models.JSONField(default=dict)                  # the full type-specific blob
    ingested_at = models.DateTimeField(auto_now_add=True)     # when WE stored it
Why event_id is unique The firehose overlaps — poll it twice and you'll see the same events again. A unique=True constraint on GitHub's own id makes the database itself reject duplicates, so ingestion can be naive and still be correct. That's your dedup safety net, enforced where it can't be bypassed.
Why a JSONField for payload Every event type has a different payload shape (a push has commits, a star has none). Rather than model 15 event types, we keep the common columns flat and stash the variable part in one JSON column. Postgres stores it as jsonb and can even query inside it later.

Pass 2 — make it queryable

Teach. You'll almost always filter events by type, by repo_name, and sort newest-first by created_at. Unindexed, each of those is a full table scan. Add db_index=True to the hot columns and a default ordering via an inner Meta class, plus a __str__ so objects are readable in the shell and admin.

events/models.py — add the lines marked # + 
class GithubEvent(models.Model):
    event_id = models.CharField(max_length=32, unique=True)
    type = models.CharField(max_length=64, db_index=True)          # + index
    actor_login = models.CharField(max_length=255, db_index=True)  # + index
    repo_name = models.CharField(max_length=255, db_index=True)    # + index
    created_at = models.DateTimeField(db_index=True)               # + index
    payload = models.JSONField(default=dict)
    ingested_at = models.DateTimeField(auto_now_add=True)

    class Meta:                            # + default ordering
        ordering = ["-created_at"]         # newest first, everywhere

    def __str__(self):                     # + readable repr
        return f"{self.type} by {self.actor_login} on {self.repo_name}"

We can't migrate yet — there's no database running. That's the next step. Leave the model here.

Your Rep: GitHub events have a public boolean and an optional org. Add an is_public BooleanField (default True) and an org_login CharField that's allowed to be empty. Which one needs null/blank handling, and why?
Solution — the two extra fields code
events/models.py — inside GithubEvent 
    is_public = models.BooleanField(default=True)
    org_login = models.CharField(max_length=255, blank=True, default="")
Why blank+default, not null For text, the Django convention is to store "no value" as the empty string (default="", blank=True) rather than NULL, so you never have to check for two kinds of "empty." blank=True is the validation rule (forms/serializers allow it); null=True is the database rule. is_public is a real boolean with a sensible default, so it needs neither.

5 · A read-only API with DRF

Teach. DRF turns a model into a JSON API with three pieces: a serializer (model ⇄ JSON), a viewset (the endpoint behavior), and a router (URL wiring). Since events come from GitHub, our API is read-only — a ReadOnlyModelViewSet gives you list + detail and nothing that writes.

Step 1 — the serializer

Build along: a serializer that exposes the event fields as JSON.
events/serializers.py 
from rest_framework import serializers
from .models import GithubEvent


class GithubEventSerializer(serializers.ModelSerializer):
    class Meta:
        model = GithubEvent
        fields = ["event_id", "type", "actor_login", "repo_name",
                  "created_at", "payload", "ingested_at"]

Step 2 — the viewset

Build the endpoint on top of the serializer. Start with the plainest possible list, then layer on query-param filtering so you see where it plugs in.

events/views.py — first pass (list + detail) 
from rest_framework import viewsets
from .models import GithubEvent
from .serializers import GithubEventSerializer


class GithubEventViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = GithubEvent.objects.all()          # Meta.ordering -> newest first
    serializer_class = GithubEventSerializer

Now let callers narrow by ?type= and ?actor= by overriding get_queryset. This is the one change — the new method marked # +:

events/views.py — add filtering 
class GithubEventViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = GithubEvent.objects.all()
    serializer_class = GithubEventSerializer

    def get_queryset(self):                    # + query-param filtering
        qs = super().get_queryset()
        event_type = self.request.query_params.get("type")
        actor = self.request.query_params.get("actor")
        if event_type:
            qs = qs.filter(type=event_type)
        if actor:
            qs = qs.filter(actor_login=actor)
        return qs

Step 3 — wire the router + pagination

config/urls.py 
from django.contrib import admin
from django.urls import path, include
from rest_framework.routers import DefaultRouter
from events.views import GithubEventViewSet

router = DefaultRouter()
router.register(r"events", GithubEventViewSet, basename="event")

urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/", include(router.urls)),      # -> /api/events/ and /api/events/<pk>/
]
config/settings.py — add near the bottom 
REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.PageNumberPagination",
    "PAGE_SIZE": 25,
}
Why a router DefaultRouter generates the URL patterns for a viewset for you — list, detail, and a browsable API root — from one register() line. Pagination is global here so no single endpoint can accidentally return 10,000 rows.
Your Rep: add a third filter, ?repo=, that matches repo_name. Then decide: should it be an exact match or a "contains" match? Implement the one you'd want as a user of a search-y API.
Solution — the repo filter code
events/views.py — inside get_queryset, before return qs 
        repo = self.request.query_params.get("repo")
        if repo:
            qs = qs.filter(repo_name__icontains=repo)   # substring, case-insensitive
Why icontains here A user searching repo=linux expects torvalds/linux to match — exact match on owner/repo would be almost useless. But note: icontains can't use the plain index and gets slow on big tables. That limitation is exactly the itch Elasticsearch scratches, which is where we go next. 6 · Ingest real GitHub events

Teach. Time for real data. A Django management command is a script with full ORM access, run via manage.py. Ours will fetch a page of events from GitHub, normalize each into our model shape, and get_or_create so re-runs don't duplicate. We'll build the command in two passes: first the fetch, then the save.

Pass 1 — fetch a page

The package layout for a command matters — Django discovers it by path:

# Create the package files Django looks for:
mkdir -p events/management/commands
touch events/management/__init__.py events/management/commands/__init__.py
events/management/commands/ingest_events.py — fetch only 
import os
import requests
from django.core.management.base import BaseCommand


class Command(BaseCommand):
    help = "Fetch recent public events from the GitHub API."

    def handle(self, *args, **options):
        headers = {"Accept": "application/vnd.github+json"}
        token = os.environ.get("GITHUB_TOKEN")
        if token:
            headers["Authorization"] = f"Bearer {token}"

        resp = requests.get("https://api.github.com/events",
                            headers=headers, params={"per_page": 100}, timeout=10)
        resp.raise_for_status()
        events = resp.json()
        self.stdout.write(f"Fetched {len(events)} events")

Pass 2 — normalize & save

Teach. Each raw event is a nested dict. Pull out the flat columns, keep the rest in payload, and let the unique constraint handle dedup. Add the save loop:

from events.models import GithubEvent

        for e in events:
            _, was_created = GithubEvent.objects.get_or_create(
                event_id=e["id"],

                    "type": e["type"],
                    "actor_login": e["actor"]["login"],
                    "repo_name": e["repo"]["name"],
                    "created_at": parse_datetime(e["created_at"]),
                    "payload": e.get("payload", {}),
                    "is_public": e.get("public", True),
                    "org_login": e.get("org", {}).get("login", "") if e.get("org") else "",
                },

            if interval <= 0:

            time.sleep(interval)

        ...   # the fetch + save code from above moves here

7 · Run Elasticsearch

Teach. Postgres finds rows by exact/indexed match. Elasticsearch builds an inverted index: it tokenizes text and maps each term → the documents containing it, so "find every event mentioning kubernetes, ranked by relevance" is instant. That's a different data structure than a B-tree, and it's why search engines exist alongside databases.

Build along: add Elasticsearch as a second Compose service. Single-node, security off — this is local dev, not production.
docker-compose.yml — add the search service 
  search:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.13.4
    environment:
      discovery.type: single-node          # don't try to form a cluster
      xpack.security.enabled: "false"      # no TLS/auth for local dev
      ES_JAVA_OPTS: "-Xms512m -Xmx512m"    # cap the heap so it fits your laptop
    ports:
      - "9200:9200"

8 · Index events into Elasticsearch

Teach. A mapping is ES's schema: it tells ES which fields are full-text (analyzed into terms) vs exact keywords (filtered/aggregated as-is). We'll make a small ES helper module, create the index with an explicit mapping, then bulk-load everything already in Postgres.

Step 1 — a shared client + mapping

events/search.py — the ES client and index definition 
import os
from elasticsearch import Elasticsearch

es = Elasticsearch(os.environ.get("ES_URL", "http://localhost:9200"))

INDEX = "github-events"

MAPPING = {
    "mappings": {
        "properties": {
            "type":        {"type": "keyword"},   # exact: filter/aggregate
            "actor_login": {"type": "keyword"},
            "repo_name":   {"type": "text",        # analyzed for search...
                            "fields": {"raw": {"type": "keyword"}}},  # ...+ exact subfield
            "message":     {"type": "text"},       # commit/issue text -> full-text
            "created_at":  {"type": "date"},
        }
    }
}


def ensure_index():
    if not es.indices.exists(index=INDEX):
        es.indices.create(index=INDEX, body=MAPPING)
Why text + a keyword subfield repo_name needs both jobs: full-text search (so "linux" matches "torvalds/linux") and exact grouping (top repos by count). ES's fields lets one source field be indexed two ways — repo_name for search, repo_name.raw for exact aggregations. keyword fields are not analyzed; text fields are broken into terms.

Step 2 — turn a model row into an ES document

The message field doesn't exist on the model — we derive it from the payload so there's something meaty to full-text search. Build the transform, then a bulk loader on top of it:

events/search.py — add the doc builder 
def _extract_message(payload: dict) -> str:
    # Different event types hide their human text in different places.
    commits = payload.get("commits") or []
    if commits:
        return " ".join(c.get("message", "") for c in commits)
    if "issue" in payload:
        return payload["issue"].get("title", "")
    if "pull_request" in payload:
        return payload["pull_request"].get("title", "")
    return payload.get("action", "")   # e.g. "started" for a star


def to_document(event) -> dict:
    return {
        "type": event.type,
        "actor_login": event.actor_login,
        "repo_name": event.repo_name,
        "message": _extract_message(event.payload),
        "created_at": event.created_at.isoformat(),
    }
events/search.py — add the bulk reindex 
from elasticsearch.helpers import bulk

def reindex_all(queryset) -> int:
    ensure_index()
    actions = (
        {"_index": INDEX, "_id": e.event_id, "_source": to_document(e)}
        for e in queryset.iterator()
    )
    count, _ = bulk(es, actions)
    es.indices.refresh(index=INDEX)   # make docs searchable immediately
    return count

                index_one(obj)   # obj is the first item of the get_or_create tuple
Gotcha — the coupling you just created Now every ingest does a synchronous ES write inline. If ES is slow or down, ingestion stalls or errors. That tight coupling between "save to Postgres" and "index in ES" is the exact problem Kafka solves in Project 3: the producer just emits an event and moves on; a separate consumer indexes at its own pace. Keep this coupling in mind — it's the cliffhanger.

9 · Build the search endpoint

Teach. Now the payoff: a GET /api/search that runs an ES query and returns ranked results. We'll grow the query DSL in passes — start with a bare full-text match, then add filters, then pagination — so you understand each clause of a bool query rather than copy a finished blob.

Pass 1 — a bare full-text match

events/views.py — add a search view 
from rest_framework.views import APIView
from rest_framework.response import Response
from .search import es, INDEX


class SearchView(APIView):
    def get(self, request):
        q = request.query_params.get("q", "")
        body = {
            "query": {
                "multi_match": {
                    "query": q,
                    "fields": ["message", "repo_name", "actor_login"],
                }
            }
        }
        res = es.search(index=INDEX, body=body)
        hits = [h["_source"] | {"score": h["_score"]} for h in res["hits"]["hits"]]
        return Response({"total": res["hits"]["total"]["value"], "results": hits})
Why multi_match It runs the same query text across several fields and takes the best score per document — so "kubernetes" hits whether it appears in a commit message, a repo name, or (unlikely) a username. The _score is ES's relevance ranking; returning it lets you see why results are ordered as they are.

Pass 2 — add filters with a bool query

Teach. A bool query composes clauses: must affects score (the search), filter narrows without affecting score (exact type/actor). Restructure the body — this is the meaningful change:

events/views.py — replace the body in SearchView.get 
        q = request.query_params.get("q", "")
        event_type = request.query_params.get("type")
        actor = request.query_params.get("actor")

        must = []
        if q:
            must.append({"multi_match": {"query": q,
                        "fields": ["message", "repo_name", "actor_login"]}})
        else:
            must.append({"match_all": {}})        # no q -> everything, still filterable

        filters = []
        if event_type:
            filters.append({"term": {"type": event_type}})
        if actor:
            filters.append({"term": {"actor_login": actor}})

        body = {"query": {"bool": {"must": must, "filter": filters}}}

Pass 3 — pagination + sort

Add from/size paging on top of the body you just built:

events/views.py — before the es.search call 
        page = int(request.query_params.get("page", 1))
        size = min(int(request.query_params.get("size", 25)), 100)  # cap it
        body["from"] = (page - 1) * size
        body["size"] = size
        body["sort"] = ["_score", {"created_at": "desc"}]   # relevance, then newest
config/urls.py — register the route 
from events.views import GithubEventViewSet, SearchView
# ...in urlpatterns, above the router include:
    path("api/search", SearchView.as_view(), name="search"),
Solution — search it end to end commands 
# Full-text across everything you've ingested
http ":8000/api/search?q=fix"

# Full-text + an exact filter
http ":8000/api/search?q=fix&type=PushEvent"

# No query, pure filter + paging
http ":8000/api/search?actor=torvalds&page=1&size=10"
must vs filter — the payoff Put type=PushEvent in filter, not must, and ES skips scoring it and can cache the result set — filters are reusable across queries. must clauses compute relevance; filters just include/exclude. Getting this split right is most of writing good ES queries.
Your Rep: add GET /api/stats that returns the top 10 repos by event count — an ES aggregation, not a search. (Hint: size: 0 to skip hits, and a terms aggregation on repo_name.raw — remember why you made that .raw subfield.)
Solution — a terms aggregation code
events/views.py 
class StatsView(APIView):
    def get(self, request):
        body = {
            "size": 0,   # we only want the aggregation, not documents
            "aggs": {
                "top_repos": {
                    "terms": {"field": "repo_name.raw", "size": 10}
                }
            },
        }
        res = es.search(index=INDEX, body=body)
        buckets = res["aggregations"]["top_repos"]["buckets"]
        return Response([{"repo": b["key"], "events": b["doc_count"]} for b in buckets])
Why .raw, not repo_name Aggregating on the analyzed text field would group by token — "torvalds" and "linux" counted separately. The keyword subfield holds the whole owner/repo string un-analyzed, so the bucket keys are real repo names. This is the concrete reason the dual mapping earned its keep two steps ago.

Teach. Inside Compose, services reach each other by service name, not localhost — so the app talks to db:5432 and search:9200. depends_on controls start order. Add the new web service:

11 · Recap, extensions & what's next

You built a real search platform over a live public firehose. Make sure you can explain each piece in your own words — that recall is the deliverable:

  • Django/DRF: model → migration → serializer → viewset → router; a read-only API with filters and pagination.
  • Postgres: env-driven config, the durable source of truth, unique constraints as a dedup net.
  • GitHub API: polling a sliding-window firehose, auth for rate limits, normalizing messy nested JSON.
  • Elasticsearch: inverted index, mappings (text vs keyword), bulk + idempotent indexing, bool queries (must vs filter), aggregations.
  • Docker Compose: a three-service stack, service-name networking, one image in two roles.

Extensions to deepen each skill

  • Add date-range filtering to search (range on created_at) with from/to params.
  • Add an aggregation for events per type and a second for events per hour (a date_histogram).
  • Highlight matched terms in results with ES highlight.
  • Add a health endpoint that checks both Postgres and ES — you'll want it for Kubernetes probes.
  • Write one test: ingest a canned event fixture, reindex, assert search finds it.
The cliffhanger → Project 3 You planted two deliberate pain points: ingestion polls from a loop, and each save does a synchronous ES write inline. Both couple things that shouldn't be coupled — if ES hiccups, ingestion suffers. Project 2 first gives the platform a face — a FastAPI search service and a Nuxt UI on top of this data. Then Project 3 fixes the coupling: Django produces a CloudEvent to Kafka and returns; a separate consumer indexes into ES at its own pace; and the whole thing runs on Kubernetes (with CKAD/CKA drills baked in) instead of Compose. Same app, real decoupling.
