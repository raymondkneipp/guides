0 · Architecture, model & permission ladder

The whole point of this project is the permission ladder — four roles with genuinely different powers over the same resources. Hold these two pictures in your head before any code.

DATA MODEL (3 levels → nested serializers) ASYNC (Kafka) Service ──< Incident ──< Update Incident opened/updated/resolved (admin) (user owns) (staff posts) │ publish event ▼ topic: incident-events │ consume ▼ Consumer → ActivityLog + "notify" PERMISSION LADDER run the whole thing on Kubernetes anonymous → read public status (API + consumer + Postgres + Kafka) user → open incidents, edit OWN staff → post updates, resolve ANY admin → manage Services, delete ANY
ActionAnonymousUserStaffAdmin
Read services / incidents✓✓✓✓
Open an incident✗✓✓✓
Edit / delete an incident✗own onlyown only✓ any
Post update / resolve incident✗✗✓✓
Create / manage a Service✗✗✗✓
Why this shape This is how real incident tools work: anyone can see the status page, the person who hit the problem opens the incident, the on-call responders (staff) drive it, and only admins touch the catalog of services. Implementing that cleanly is the difference between a toy API and a real one — and it's exactly the permission modeling interviewers and code reviewers care about.

2 · Models: Service → Incident → Update

Three levels of nesting. A Service has many Incidents; an Incident has many Updates (its timeline). Ownership lives on the incident (reported_by) and each update (author).

Your task: model all three, with severity/status choices on the incident and FK ownership fields pointing at the user.
Solution — incidents/models.py code
incidents/models.py 
from django.conf import settings
from django.db import models


class Service(models.Model):
    name = models.CharField(max_length=120, unique=True)
    description = models.TextField(blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.name


class Incident(models.Model):
    class Severity(models.TextChoices):
        SEV1 = "SEV1", "Critical"
        SEV2 = "SEV2", "Major"
        SEV3 = "SEV3", "Minor"

    class Status(models.TextChoices):
        OPEN = "open", "Open"
        MONITORING = "monitoring", "Monitoring"
        RESOLVED = "resolved", "Resolved"

    service = models.ForeignKey(Service, related_name="incidents", on_delete=models.CASCADE)
    title = models.CharField(max_length=200)
    severity = models.CharField(max_length=4, choices=Severity.choices, default=Severity.SEV3)
    status = models.CharField(max_length=12, choices=Status.choices, default=Status.OPEN)
    reported_by = models.ForeignKey(settings.AUTH_USER_MODEL, related_name="incidents",
                                    on_delete=models.CASCADE)
    created_at = models.DateTimeField(auto_now_add=True)
    resolved_at = models.DateTimeField(null=True, blank=True)

    class Meta:
        ordering = ["-created_at"]

    def __str__(self):
        return f"[{self.severity}] {self.title}"


class Update(models.Model):
    incident = models.ForeignKey(Incident, related_name="updates", on_delete=models.CASCADE)
    message = models.TextField()
    author = models.ForeignKey(settings.AUTH_USER_MODEL, related_name="updates",
                               on_delete=models.CASCADE)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["created_at"]


class ActivityLog(models.Model):
    """Written by the Kafka consumer, never by the API directly."""
    event_type = models.CharField(max_length=40)
    payload = models.JSONField()
    created_at = models.DateTimeField(auto_now_add=True)
Why related_name related_name="incidents" and related_name="updates" are what make the nested serializers clean — you'll write service.incidents and incident.updates and DRF will nest them automatically. Get these names right now and step 4 is trivial.

4 · Nested serializers — reading

The first half of nested serializers: representation. When you GET an incident, its updates should come back inline; when you GET a service, its incidents nest underneath.

Your task: build UpdateSerializer, an IncidentSerializer that nests updates read-only, and a ServiceSerializer that nests incidents.
Solution — read serializers code
incidents/serializers.py — replace step 3's flat version with these nested ones 
from rest_framework import serializers
from .models import Service, Incident, Update


class UpdateSerializer(serializers.ModelSerializer):
    author = serializers.ReadOnlyField(source="author.username")

    class Meta:
        model = Update
        fields = ["id", "message", "author", "created_at"]
        read_only_fields = ["author", "created_at"]


class IncidentSerializer(serializers.ModelSerializer):
    updates = UpdateSerializer(many=True, read_only=True)        # <-- nested read
    reported_by = serializers.ReadOnlyField(source="reported_by.username")

    class Meta:
        model = Incident
        fields = ["id", "service", "title", "severity", "status",
                  "reported_by", "created_at", "resolved_at", "updates"]
        read_only_fields = ["status", "reported_by", "created_at", "resolved_at", "updates"]


class ServiceSerializer(serializers.ModelSerializer):
    incidents = IncidentSerializer(many=True, read_only=True)    # <-- nested read

    class Meta:
        model = Service
        fields = ["id", "name", "description", "created_at", "incidents"]
Gotcha — N+1 queries Nesting reads is easy to write and easy to make slow. Each nested serializer triggers extra queries per parent row. You'll fix this in the ViewSet with select_related/prefetch_related (step 8). Nesting without prefetching is the classic DRF performance trap.

5 · Nested serializers — writing

The hard half, and the part most tutorials dodge: accepting nested data. We want to open an incident and post its first update in a single POST. DRF won't do nested writes for you — you override create().

Your task: an IncidentCreateSerializer that accepts an optional updates list and, in create(), makes the incident + each update, stamping the current user as owner/author.
Solution — write serializer with create() override code
incidents/serializers.py — add this 
class IncidentCreateSerializer(serializers.ModelSerializer):
    updates = UpdateSerializer(many=True, required=False)        # accept nested input

    class Meta:
        model = Incident
        fields = ["id", "service", "title", "severity", "updates"]

    def create(self, validated_data):
        updates_data = validated_data.pop("updates", [])
        user = self.context["request"].user                      # who's making the call
        incident = Incident.objects.create(reported_by=user, **validated_data)
        for update in updates_data:
            Update.objects.create(incident=incident, author=user, **update)
        return incident
Why a separate create serializer Reading and writing want different shapes — reads nest full objects and expose status/timestamps; writes accept only what the client may set and pull the user from the request, not the payload. Splitting them (and selecting per-action in the ViewSet) is cleaner than one serializer bristling with conditionals. Note we get the user from self.context["request"] — DRF injects that automatically, so the client can never spoof ownership by sending a reported_by field.

7 · Public-read / auth-write + ownership

Now the ladder. Rung 1-2: anyone reads, logged-in users write, and a user can only edit/delete their own incident. That last bit is an object-level permission.

Your task: write an IsOwnerOrReadOnly object permission, then a IncidentViewSet that uses it plus IsAuthenticatedOrReadOnly, selects the create serializer for creates, and prefetches to kill the N+1.
Solution — custom permissions code
incidents/permissions.py 
from rest_framework import permissions


class IsOwnerOrReadOnly(permissions.BasePermission):
    """Anyone may read; only the owner may modify."""
    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:
            return True
        owner = getattr(obj, "reported_by", None) or getattr(obj, "author", None)
        return owner == request.user


class IsStaffMember(permissions.BasePermission):
    """Responder tier."""
    def has_permission(self, request, view):
        return bool(request.user and request.user.is_staff)


class IsSuperuserOrReadOnly(permissions.BasePermission):
    """Admin tier — superuser writes, everyone reads."""
    def has_permission(self, request, view):
        if request.method in permissions.SAFE_METHODS:
            return True
        return bool(request.user and request.user.is_superuser)
Solution — IncidentViewSet code
incidents/views.py — the full IncidentViewSet (replaces step 3's starter) 
from django.utils import timezone
from rest_framework import viewsets, permissions, status
from rest_framework.decorators import action
from rest_framework.response import Response

from .models import Service, Incident
from .serializers import (ServiceSerializer, IncidentSerializer,
                          IncidentCreateSerializer, UpdateSerializer)
from .permissions import IsOwnerOrReadOnly, IsStaffMember, IsSuperuserOrReadOnly
from .kafka import publish_event


class IncidentViewSet(viewsets.ModelViewSet):
    queryset = (Incident.objects
                .select_related("service", "reported_by")
                .prefetch_related("updates__author"))           # kills the N+1
    permission_classes = [permissions.IsAuthenticatedOrReadOnly, IsOwnerOrReadOnly]

    def get_serializer_class(self):
        return IncidentCreateSerializer if self.action == "create" else IncidentSerializer

    def perform_create(self, serializer):
        incident = serializer.save()                            # owner set in serializer.create()
        publish_event("incident.opened", {
            "id": incident.id, "service": incident.service_id,
            "severity": incident.severity, "title": incident.title,
        })
Gotcha — when object permissions fire has_object_permission only runs on detail actions that call get_object() (retrieve/update/destroy). It does not run on list or create — list filtering and "who can create" are has_permission's job. Mixing these up is the #1 reason people think their permission "isn't working."

8 · Staff checks — the moderation action

Rung 3: responders (staff) drive incidents — they post updates to the timeline and resolve. These aren't plain CRUD on the incident, they're custom actions with their own permission.

Your task: add two @action endpoints to the ViewSet — POST /api/incidents/{id}/updates/ and POST /api/incidents/{id}/resolve/ — both gated to staff, both firing a Kafka event.
Solution — staff actions code
incidents/views.py — add inside IncidentViewSet 
    @action(detail=True, methods=["post"],
            permission_classes=[permissions.IsAuthenticated, IsStaffMember])
    def updates(self, request, pk=None):
        """Staff posts an update to the incident timeline."""
        incident = self.get_object()
        serializer = UpdateSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        update = serializer.save(incident=incident, author=request.user)
        publish_event("incident.updated", {"id": incident.id, "message": update.message})
        return Response(UpdateSerializer(update).data, status=status.HTTP_201_CREATED)

    @action(detail=True, methods=["post"],
            permission_classes=[permissions.IsAuthenticated, IsStaffMember])
    def resolve(self, request, pk=None):
        """Staff resolves the incident."""
        incident = self.get_object()
        incident.status = Incident.Status.RESOLVED
        incident.resolved_at = timezone.now()
        incident.save(update_fields=["status", "resolved_at"])
        publish_event("incident.resolved", {"id": incident.id})
        return Response({"status": "resolved"})
Why per-action permissions permission_classes on an @action override the ViewSet's defaults for just that endpoint. So owning an incident lets you edit its fields, but only staff can drive the timeline — two different powers on the same object, expressed cleanly. This is exactly how you model "the reporter opened it, but on-call runs it."

9 · Admin checks

Rung 4: only admins (superusers) manage the catalog of Services. Everyone else reads.

Your task: a ServiceViewSet guarded by IsSuperuserOrReadOnly.
Solution — ServiceViewSet code
incidents/views.py — add 
class ServiceViewSet(viewsets.ModelViewSet):
    queryset = Service.objects.prefetch_related("incidents__updates")
    serializer_class = ServiceSerializer
    permission_classes = [IsSuperuserOrReadOnly]
Gotcha — DRF's IsAdminUser is a trap DRF ships permissions.IsAdminUser — but it checks is_staff, NOT is_superuser. So "admin" in DRF means "staff." Because we want a real distinction between staff and admin, we wrote our own IsSuperuserOrReadOnly keyed on is_superuser. If you'd used the built-in, your staff would've had admin powers by accident — a real-world security bug.

10 · The permission-matrix tests

This is the payoff section. The whole value of a permission ladder is that it's correct — so you test the matrix: every role against every action gets the right 200 / 401 / 403.

Your task: an APITestCase that creates all four roles and asserts: anon can read but not write, a user can open an incident but not resolve it, only the owner can edit, only staff can resolve, only admin can create a service.
Solution — incidents/tests.py code
incidents/tests.py 
from django.contrib.auth import get_user_model
from rest_framework import status
from rest_framework.test import APITestCase
from .models import Service, Incident

User = get_user_model()


class PermissionMatrix(APITestCase):
    @classmethod
    def setUpTestData(cls):
        cls.alice = User.objects.create_user("alice", password="pw")
        cls.bob = User.objects.create_user("bob", password="pw")
        cls.sam = User.objects.create_user("sam", password="pw", is_staff=True)
        cls.root = User.objects.create_superuser("root", password="pw")
        cls.svc = Service.objects.create(name="API Gateway")

    def _incident(self, owner):
        return Incident.objects.create(service=self.svc, title="DB down",
                                       severity="SEV1", reported_by=owner)

    def test_anonymous_reads_but_cannot_write(self):
        self.assertEqual(self.client.get("/api/incidents/").status_code, 200)
        r = self.client.post("/api/incidents/", {"service": self.svc.id, "title": "x"}, format="json")
        self.assertIn(r.status_code, (401, 403))

    def test_user_can_open_incident(self):
        self.client.force_authenticate(self.alice)
        r = self.client.post("/api/incidents/",
                             {"service": self.svc.id, "title": "Latency spike", "severity": "SEV2"},
                             format="json")
        self.assertEqual(r.status_code, 201)

    def test_only_owner_can_edit(self):
        inc = self._incident(self.alice)
        self.client.force_authenticate(self.bob)                 # not the owner
        r = self.client.patch(f"/api/incidents/{inc.id}/", {"title": "hijack"}, format="json")
        self.assertEqual(r.status_code, 403)

    def test_only_staff_can_resolve(self):
        inc = self._incident(self.alice)
        self.client.force_authenticate(self.alice)               # owner, but not staff
        self.assertEqual(self.client.post(f"/api/incidents/{inc.id}/resolve/").status_code, 403)
        self.client.force_authenticate(self.sam)                 # staff
        self.assertEqual(self.client.post(f"/api/incidents/{inc.id}/resolve/").status_code, 200)

    def test_only_admin_creates_service(self):
        self.client.force_authenticate(self.sam)                 # staff is not enough
        self.assertEqual(self.client.post("/api/services/", {"name": "Cache"}, format="json").status_code, 403)
        self.client.force_authenticate(self.root)                # admin
        self.assertEqual(self.client.post("/api/services/", {"name": "Cache"}, format="json").status_code, 201)
uv run python manage.py test incidents
Why this matters A permission bug doesn't throw an error — it silently lets the wrong person do the wrong thing. The matrix test is the only thing that proves your ladder actually holds. This is also the single most impressive thing to show in a code review or interview: "here's the access model, and here's the test suite that enforces it."

11 · Kafka — publish incident events

You've already been calling publish_event(...) in the views. Now write it. Every incident lifecycle change emits an event — fire-and-forget, never blocking the API response.

Your task: a publish_event helper using confluent-kafka, bootstrap server from env, to topic incident-events.
Solution — incidents/kafka.py code
incidents/kafka.py 
import json
import os
from confluent_kafka import Producer

_producer = Producer({
    "bootstrap.servers": os.environ.get("KAFKA_BOOTSTRAP_SERVERS", "localhost:9092"),
    "client.id": "incident-api",
})
TOPIC = "incident-events"


def publish_event(event_type: str, data: dict) -> None:
    payload = {"type": event_type, "data": data}
    try:
        _producer.produce(TOPIC, key=str(data.get("id", "")), value=json.dumps(payload))
        _producer.poll(0)            # service delivery callbacks without blocking
    except BufferError:
        pass                          # never fail an API request over telemetry
Why keyed by incident id Keying on the incident id sends all events for one incident to the same partition, preserving their order (opened → updated → resolved) even when you scale consumers. And we swallow errors — the API's job is to respond fast; analytics/notifications are the consumer's problem.

12 · Kafka consumer — activity feed

A separate process consumes incident-events and writes an ActivityLog (and in real life, fires Slack/PagerDuty notifications). The API never does this work — that's the decoupling.

Your task: a management command consume_events that reads the topic and records each event, ignoring the harmless "topic not ready yet" blip.
Solution — incidents/management/commands/consume_events.py code
incidents/management/commands/consume_events.py 
# Create the empty package files first:
#   incidents/management/__init__.py
#   incidents/management/commands/__init__.py
import json
import os
from confluent_kafka import Consumer, KafkaError
from django.core.management.base import BaseCommand
from incidents.models import ActivityLog


class Command(BaseCommand):
    help = "Consume incident-events and build the activity feed."

    def handle(self, *args, **options):
        consumer = Consumer({
            "bootstrap.servers": os.environ.get("KAFKA_BOOTSTRAP_SERVERS", "localhost:9092"),
            "group.id": "incident-processor",
            "auto.offset.reset": "earliest",
        })
        consumer.subscribe(["incident-events"])
        self.stdout.write(self.style.SUCCESS("Listening on incident-events..."))
        try:
            while True:
                msg = consumer.poll(1.0)
                if msg is None:
                    continue
                if msg.error():
                    if msg.error().code() == KafkaError._UNKNOWN_TOPIC_OR_PART:
                        continue       # topic not created until first publish — harmless
                    self.stderr.write(f"Kafka error: {msg.error()}")
                    continue
                event = json.loads(msg.value())
                ActivityLog.objects.create(event_type=event["type"], payload=event["data"])
                self.stdout.write(f"🔔 {event['type']} → {event['data']}")
        finally:
            consumer.close()
Why a consumer group group.id="incident-processor" means you can run one replica (it gets everything) or three (Kafka splits the partitions across them) with zero code change. Add a second group later — say "slack-notifier" — and it gets its own independent copy of the whole event stream. That fan-out is why incidents go through Kafka instead of a direct function call.

class SerializerTests(APITestCase):
    @classmethod
    def setUpTestData(cls):
        cls.alice = User.objects.create_user("alice", password="pw")
        cls.bob = User.objects.create_user("bob", password="pw")
        cls.svc = Service.objects.create(name="API Gateway")

    def test_create_incident_with_nested_updates(self):
        self.client.force_authenticate(self.alice)
        payload = {
            "service": self.svc.id, "title": "DB down", "severity": "SEV1",
            "updates": [{"message": "investigating"}, {"message": "rolling back"}],
        }
        r = self.client.post("/api/incidents/", payload, format="json")
        self.assertEqual(r.status_code, 201)
        inc = Incident.objects.get(id=r.data["id"])
        self.assertEqual(inc.updates.count(), 2)
        self.assertEqual(inc.reported_by, self.alice)        # owner stamped from request

    def test_client_cannot_spoof_owner(self):
        self.client.force_authenticate(self.alice)
        r = self.client.post("/api/incidents/",
            {"service": self.svc.id, "title": "x", "reported_by": self.bob.id}, format="json")
        self.assertEqual(r.status_code, 201)
        # reported_by came from the request user, NOT the payload:
        self.assertEqual(Incident.objects.get(id=r.data["id"]).reported_by, self.alice)
Why test the spoof case The "can't spoof owner" test guards a real security property. Someone will try sending reported_by in the payload; this proves your serializer ignores it and trusts the authenticated request instead. Tests like this document your security decisions.

from unittest.mock import patch


class EventPublishingTests(APITestCase):
    @classmethod
    def setUpTestData(cls):
        cls.alice = User.objects.create_user("alice", password="pw")
        cls.sam = User.objects.create_user("sam", password="pw", is_staff=True)
        cls.svc = Service.objects.create(name="API Gateway")

    @patch("incidents.views.publish_event")          # patch where it's USED
    def test_opening_incident_publishes_event(self, mock_publish):
        self.client.force_authenticate(self.alice)
        self.client.post("/api/incidents/",
            {"service": self.svc.id, "title": "DB down", "severity": "SEV1"}, format="json")
        mock_publish.assert_called_once()
        event_type, _data = mock_publish.call_args.args
        self.assertEqual(event_type, "incident.opened")

    @patch("incidents.views.publish_event")
    def test_resolving_publishes_event(self, mock_publish):
        inc = Incident.objects.create(service=self.svc, title="x", reported_by=self.alice)
        self.client.force_authenticate(self.sam)
        self.client.post(f"/api/incidents/{inc.id}/resolve/")
        mock_publish.assert_called_with("incident.resolved", {"id": inc.id})
Gotcha — patch where it's USED, not defined We patch incidents.views.publish_event, not incidents.kafka.publish_event. Because views.py did from .kafka import publish_event, the name lives in the views module's namespace — that's the reference your view actually calls. Patching the original in kafka.py would do nothing. This trips up everyone the first time. Mocking it also means your tests never need a real Kafka broker — fast and hermetic.

import json
from incidents.models import ActivityLog


def record_event(raw_value: str) -> ActivityLog:
    """Pure-ish logic: take a raw Kafka message value, write an ActivityLog."""
    event = json.loads(raw_value)
    return ActivityLog.objects.create(event_type=event["type"], payload=event["data"])

from django.test import TestCase
from incidents.events import record_event
from incidents.models import ActivityLog


class ConsumerLogicTests(TestCase):
    def test_record_event_writes_activity_log(self):
        log = record_event('{"type": "incident.opened", "data": {"id": 1}}')
        self.assertEqual(log.event_type, "incident.opened")
        self.assertEqual(ActivityLog.objects.count(), 1)
The pattern: separate I/O from logic The Kafka while True loop is I/O — hard to test. The decision (parse → write) is logic — easy to test. Pulling the logic into record_event() lets you unit-test the part that matters without spinning up a broker. This "thin I/O shell around testable logic" pattern applies everywhere — it's one of the highest-leverage testing habits you can build.
