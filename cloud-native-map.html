The Cloud-Native Map

Docker, Kubernetes, Helm, Knative and the tools around them: what each piece does, how they snap together, and which ones are worth learning first. Reference doc, no build-along. Last reviewed October 2026.

01One-sentence versions

DockerPackages your app + its whole environment into an image, and runs it as a container.The shipping container.
KubernetesRuns lots of containers across lots of machines, and keeps them running the way you described.The port + crane operators + harbor master.
HelmBundles a pile of Kubernetes YAML into one versioned, configurable package.apt / brew / npm, for Kubernetes apps.
KnativeAdds serverless on top of K8s: give it a container, get a URL that scales to zero.Your own Cloud Run / Lambda, on your cluster.
Argo CDKeeps the cluster in sync with what is in a git repo.git push is the deploy button.
PrometheusScrapes numbers from everything and alerts when they look wrong.The dashboard gauges + warning lights.
The thing people get wrong: these are not competitors. Docker vs Kubernetes is like "engine vs car." Helm and Knative aren't alternatives to Kubernetes, they're add-ons that run inside it.

02The stack

Read it bottom-up. Your code becomes an image (Docker), a runtime starts it as a process, Kubernetes decides where and how many, extensions like Knative and KEDA teach Kubernetes new tricks, Helm packages the YAML, CI/GitOps ships it, and observability tells you if it's on fire.

03Docker: the box

A container is just a normal Linux process with blinders on: it gets its own filesystem (from the image), its own network, its own process list, and limits on CPU/RAM. No VM, no second kernel, which is why it starts in milliseconds.

FROM python:3.12-slim            # base layer
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt   # cached unless requirements change
COPY . .                          # your code: the layer that changes most, so it goes last
CMD ["gunicorn", "app.wsgi", "-b", "0.0.0.0:8000"]

Words you'll see

TermMeans
ImageRead-only template, built from a Dockerfile. Tagged like ghcr.io/ray/web:1.4.2.
ContainerA running (or stopped) instance of an image.
RegistryWhere images live: Docker Hub, GitHub (GHCR), AWS ECR, self-hosted Harbor.
OCIThe open standard for image format. Why a Docker-built image runs anywhere.
Composedocker-compose.yml: run several containers together on one machine. Great for dev; Kubernetes is its grown-up form.
containerd / runcWhat actually runs containers under Docker and under Kubernetes.
Kubernetes doesn't use Docker anymore (since v1.24). It talks to containerd or CRI-O directly. Doesn't matter to you: you still build with Docker, and those images run fine, because they're all OCI.

04Kubernetes: the fleet manager

You never tell Kubernetes do this. You tell it this is how the world should look, and it works out the steps. That one idea is the whole system:

The objects you'll actually touch

ObjectWhat it is
PodSmallest unit: 1+ containers sharing an IP. Disposable. You rarely create these directly.
Deployment"Keep N copies of this pod running, roll out updates gradually." Your default for stateless apps.
ServiceStable name + IP in front of a changing set of pods (http://web inside the cluster).
Ingress / GatewayHTTP routing from outside: host/path → Service, plus TLS.
ConfigMap / SecretConfig and credentials, injected as env vars or files.
PersistentVolumeClaim"I need 10 GB of disk that survives pod restarts."
StatefulSetLike Deployment, but pods get stable names + their own disks. Databases, Kafka.
DaemonSetOne pod on every node. Log shippers, monitoring agents.
Job / CronJobRun to completion, once or on a schedule.
NamespaceA folder for objects: dev, prod, monitoring.
CRD + OperatorTeach K8s a new object type (KafkaTopic, Certificate, a Knative Service) plus a controller that runs the loop for it. This is how the whole ecosystem plugs in.
apiVersion: apps/v1
kind: Deployment            # "keep N copies of this pod running"
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:                 # the pod
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: web
          image: ghcr.io/ray/web:1.4.2
          ports: [{ containerPort: 8000 }]
---
apiVersion: v1
kind: Service               # stable name + IP in front of those pods
metadata: { name: web }
spec:
  selector: { app: web }    # matches by label, not by pod name
  ports: [{ port: 80, targetPort: 8000 }]

05Networking: how a request finds your pod

Heads-up on Ingress: the old community ingress-nginx controller is retired, and new work goes to the Gateway API (HTTPRoute etc.). It was retired in March 2026 (announcement): no more releases or security fixes. Learn Ingress enough to read it, but build new stuff on Gateway API with Envoy Gateway, Traefik or Cilium.

06Helm: the package manager

A real app is 10–30 YAML files that are 90% identical between dev and prod. Helm turns them into one chart with knobs (values.yaml). Two ways you'll use it: consuming charts other people wrote (Postgres, Kafka, Argo, Prometheus: one command each) and authoring a chart for your own app.

# templates/deployment.yaml (inside the chart)
spec:
  replicas: {{ .Values.replicas }}
  template:
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repo }}:{{ .Values.image.tag }}"

# values.yaml (defaults)            # prod-values.yaml (override)
replicas: 1                         replicas: 4
image: { repo: ghcr.io/ray/web, tag: "1.4.2" }
helm repo add bitnami https://charts.bitnami.com/bitnami   # use someone else's chart
helm install pg bitnami/postgresql                          # a whole Postgres, one line
helm upgrade --install web ./chart -f prod-values.yaml      # your own chart
helm history web && helm rollback web 2
Helm vs Kustomize: Helm = templates + variables + release history. Kustomize = plain YAML base + small per-environment patches, no templating language. Lots of teams use both: Helm for third-party stuff, Kustomize for their own apps. Argo CD speaks both.

07Knative: serverless on your cluster

Knative is a set of CRDs + controllers you install into Kubernetes. It has two halves you can use separately:

  • Serving: one short YAML gives you a Deployment, Service, route, URL, request-based autoscaling, scale-to-zero, and immutable revisions you can split traffic between (canary: 90/10). It's what Google Cloud Run is built on.
  • Eventing: event sources (Kafka, GitHub, cron, …) publish CloudEvents into a Broker; Triggers filter by type and deliver them to services. Producers and consumers never know about each other.
apiVersion: serving.knative.dev/v1
kind: Service               # NOT a core K8s Service: Knative's own CRD
metadata: { name: hello }
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/min-scale: "0"    # scale to zero when idle
    spec:
      containers:
        - image: ghcr.io/ray/hello:2
# That's it. Knative creates the Deployment, Service, route, autoscaler, and gives you a URL.

When to reach for it (and when not)

Use Knative when…Skip it when…
Lots of small HTTP services / functions that sit idle most of the day. Scale-to-zero saves real money.
You want Cloud Run-style DX on your own cluster.
You want canary/blue-green without a service mesh.		 Steady always-on traffic: a plain Deployment + HPA is simpler.
Scaling on queue depth, not HTTP: use KEDA.
Workflows/pipelines: that's Argo Workflows' job.
Cold starts (a second or two) are unacceptable.
Knative Eventing vs Argo Events vs Kafka: Kafka is the durable pipe. Argo Events turns events into workflow runs. Knative Eventing routes events to request-driven services. They stack: a KafkaSource can feed either one.

08End to end: one commit's journey

  1. You push code. GitHub Actions runs tests, docker build, scans with Trivy, pushes web:abc123 to the registry.
  2. CI commits the new tag into the GitOps repo (a Helm values file).
  3. Argo CD notices git changed, renders the chart, applies it.
  4. Kubernetes rolls new pods in, waits for health checks, retires old ones. A bad deploy? git revert.
  5. Knative / KEDA / HPA scale with load; Prometheus scrapes everything; Grafana shows it; alerts page you.

09The rest of the toolbox

The CNCF landscape has 1,000+ logos. These are the ones that actually show up in job posts and real clusters:

Local clusters

kindK8s nodes as Docker containers. Best for learning + CI.
k3d / k3sk3s = tiny real K8s (great for a home server); k3d runs it in Docker.
minikubeThe classic single-node learning cluster.
OrbStack / Docker DesktopMac apps with a one-click cluster built in.

Driving the cluster

kubectlThe CLI. Everything else is sugar on top.
k9sTerminal UI for K8s. You will live in it.
kubectx / kubensSwitch cluster / namespace fast.
sternTail logs from many pods at once.

Packaging

HelmTemplated charts + releases. The app store of K8s.
KustomizeNo templates: base YAML + per-env patches. Built into kubectl.

GitOps & CI/CD

Argo CDWatches a git repo, syncs it into the cluster, nice UI.
FluxSame idea as Argo CD, more CLI/controller-shaped.
GitHub ActionsBuild, test, scan, push images.
Tekton / Argo WorkflowsPipelines that run as pods inside K8s.

Events & messaging

Kafka (Strimzi)Durable event log; Strimzi is the operator that runs it on K8s.
NATSLightweight messaging; JetStream adds persistence.
Argo EventsTurns events (Kafka, webhooks, cron) into workflow runs.
Knative EventingBroker + triggers, routes CloudEvents to services.

Scaling

HPABuilt-in: scale pods on CPU/memory.
KEDAScale on anything (Kafka lag, queue depth, cron), including to zero.
Cluster Autoscaler / KarpenterAdd/remove nodes (VMs) when pods do not fit.
Knative ServingRequest-based autoscale + scale-to-zero for HTTP.

Networking & traffic

Gateway APIThe modern replacement for Ingress. Learn this one.
Ingress controllersTraefik, Envoy Gateway, NGINX: route HTTP into the cluster.
cert-managerFree auto-renewing TLS certs (Let's Encrypt).
CiliumeBPF networking + network policy; the CNI to know.
Istio / LinkerdService mesh: mTLS, retries, traffic splitting between services.
external-dnsCreates DNS records from your Services/Ingresses.

Observability

PrometheusScrapes metrics, fires alerts.
GrafanaDashboards over everything.
LokiLogs, Prometheus-style.
OpenTelemetryThe standard for traces/metrics/logs from your code.

Security & secrets

TrivyScan images for CVEs in CI.
Kyverno / OPA GatekeeperPolicy: "no :latest tags", "must set limits".
External Secrets / Sealed SecretsGet secrets from Vault/AWS into K8s without committing them.
FalcoRuntime threat detection.

Infrastructure

Terraform / OpenTofuCreate the cloud stuff: VPC, the EKS cluster, DNS.
CrossplaneManage cloud resources as K8s objects.
EKS / GKE / AKSManaged K8s: the cloud runs the control plane.

10What to learn, in order

#LearnDone when you can…
1Docker + ComposeWrite a small, cached Dockerfile; run app + Postgres with Compose.
2Kubernetes core on kindDeploy with Deployment/Service/ConfigMap/Secret; debug with kubectl describe, logs, k9s.
3HelmInstall Postgres/Kafka from charts; turn your raw YAML into your own chart.
4Gateway API + cert-managerHit your app at a real hostname over HTTPS.
5Argo CDDeploy by git push only. No more kubectl apply.
6Prometheus + GrafanaSee your app's request rate and errors; get one alert.
7Kafka + KEDA / Knative / Argo EventsScale or trigger work from events.
