Python Backend Tech Stack Options

A decision doc for a team migrating off Django. Web-framework choices (Django vs FastAPI vs Litestar) and ORM choices (SQLAlchemy 2.0, SQLModel, Tortoise, Piccolo) — pros, cons, code, and a recommendation. Last reviewed July 2026.

TL;DR
  1. Framework: FastAPI is a solid move if you're API-first and benefit from async. If it's CRUD + admin heavy, don't dismiss staying on Django 5.x.
  2. ORM — safe default: SQLAlchemy 2.0 + Alembic. Boring, and boring is a feature.
  3. ORM — best DX with FastAPI: SQLModel (same author as FastAPI).
  4. ORM — familiar for Django refugees: Tortoise ORM.
  5. ORM — type-safety & speed, small ecosystem OK: Piccolo.
Biggest hidden cost of leaving Django: you don't just swap a framework — you give up the admin, auth, ORM, and migration tooling as one integrated whole, and re-assemble them from independent packages.

1. Web Framework

Django (the incumbent)

Batteries-included, convention-driven, sync-first with a maturing async story (Django 5.x has async views, middleware, and an async ORM API).

Pros: everything in one box (ORM, migrations, admin, auth, forms, sessions, CSRF); the admin site alone is worth thousands of dollars of build time; enormous ecosystem and hiring pool; great for server-rendered apps, internal tools, and structured SaaS.

Cons: the ORM is fundamentally sync — async views help with external I/O, but DB-bound workloads don't get the full async win; heavier and more opinionated; not API-first (DRF bolts on REST but feels dated next to Pydantic + auto OpenAPI).

Choose Django when: the product is CRUD + admin heavy, you want conventions over configuration, and raw async throughput isn't the bottleneck.

FastAPI (what the team is considering)

Async-first, built on Starlette + Pydantic. Type hints drive validation, serialization, dependency injection, and automatic OpenAPI/Swagger docs.

Pros: async-native — one worker juggles many concurrent I/O-bound requests; Pydantic validation and auto-generated docs are best-in-class; lightweight and fast; natural fit for microservices, AI/RAG backends, and high-throughput data APIs; type hints give real editor/mypy support end-to-end.

Cons: not batteries-included — no ORM, migrations, admin, or auth; you pick and wire each one; more architectural decisions land on the team, which can fragment large codebases without strong internal conventions; background tasks and async correctness are your problem to get right.

Choose FastAPI when: you're API-first, want async, and are comfortable assembling your own stack (ORM + Alembic + auth + admin).

Litestar (the dark-horse alternative)

An async framework in the FastAPI mold, but more batteries-included — layered dependency injection, patterns for larger apps, first-class SQLAlchemy integration, less assemble-it-yourself. Smaller community than FastAPI. If the team's worry about FastAPI is "too unstructured for a big app," Litestar is the natural thing to evaluate.

Framework verdict: a common, honest 2026 pattern is hybrid — keep Django where structure + admin matter, use FastAPI for async-heavy or high-performance services. You don't have to pick one religion for the whole org.

2. ORM Options

All snippets model the same tiny domain: a Team with many Heros.

SQLAlchemy 2.0 — the powerhouse (safe default)

The industry standard. Core + ORM, sync and async, every dialect, and Alembic — the best migration tool in the ecosystem.

from sqlalchemy import ForeignKey, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase):
    pass

class Team(Base):
    __tablename__ = "team"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50))
    heroes: Mapped[list["Hero"]] = relationship(back_populates="team")

class Hero(Base):
    __tablename__ = "hero"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50))
    team_id: Mapped[int] = mapped_column(ForeignKey("team.id"))
    team: Mapped["Team"] = relationship(back_populates="heroes")

# Async query
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

async def heroes_on(session: AsyncSession, team_name: str):
    stmt = select(Hero).join(Team).where(Team.name == team_name)
    result = await session.execute(stmt)
    return result.scalars().all()

Pros: unmatched maturity, migrations, community, escape hatches; async-native; handles any query you can dream up. Cons: steepest learning curve; verbose; not Pydantic-aware, so you hand-write request/response schemas separately from your DB models.

SQLModel — SQLAlchemy + Pydantic, by the FastAPI author

A thin layer that makes one class serve as both the Pydantic schema and the SQLAlchemy model. Actively maintained (0.0.x line, tracking SQLAlchemy 2.0).

from sqlmodel import Field, Relationship, SQLModel

class Team(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str
    heroes: list["Hero"] = Relationship(back_populates="team")

class Hero(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str
    team_id: int | None = Field(default=None, foreign_key="team.id")
    team: Team | None = Relationship(back_populates="heroes")

# The same model doubles as the FastAPI response schema:
from sqlmodel import select

async def heroes_on(session, team_name: str):
    stmt = select(Hero).join(Team).where(Team.name == team_name)
    result = await session.exec(stmt)
    return result.all()

Pros: least boilerplate with FastAPI (one model, not three); great type hints; you're really on SQLAlchemy underneath, so no lock-in. Cons: still 0.0.x and development has been stop-start; no async wrappers — you import AsyncSession/AsyncEngine straight from SQLAlchemy; for complex queries you drop to raw SQLAlchemy anyway (so you must know both).

Tortoise ORM — the Django-familiar async ORM

Async-native with an API that deliberately mirrors the Django ORM. This is the one that will feel like home for your team. Uses Aerich for migrations.

from tortoise import fields
from tortoise.models import Model

class Team(Model):
    id = fields.IntField(pk=True)
    name = fields.CharField(max_length=50)

class Hero(Model):
    id = fields.IntField(pk=True)
    name = fields.CharField(max_length=50)
    team = fields.ForeignKeyField("models.Team", related_name="heroes")

# Django-esque query API:
async def heroes_on(team_name: str):
    return await Hero.filter(team__name=team_name)

Pros: gentle on-ramp for Django devs; genuinely async; solid write performance (benchmarks put p50 latency ~a third faster than SQLAlchemy); built-in Pydantic serialization via pydantic_model_creator. Cons: Aerich migrations are noticeably less mature than Alembic (the most common production complaint); smaller ecosystem and maintainer bandwidth; fewer battle-tested large deployments.

Piccolo — type-safe, fast, batteries-ish

Async-native with its own query builder, first-class static typing (mypy/Pyright), built-in migrations, an admin UI, and an auth app.

from piccolo.columns import ForeignKey, Varchar
from piccolo.table import Table

class Team(Table):
    name = Varchar(length=50)

class Hero(Table):
    name = Varchar(length=50)
    team = ForeignKey(references=Team)

# Query builder returns awaitables:
async def heroes_on(team_name: str):
    return await Hero.objects().where(Hero.team.name == team_name)

Pros: fastest simple reads in recent benchmarks (~40% faster than SQLAlchemy at p50); excellent type safety; ships its own admin + migrations + auth, which softens the "leaving Django" pain; low memory / cold-start. Cons: community is ~50× smaller than SQLAlchemy's; sparse public production case studies; no MySQL (Postgres/SQLite only); you're betting on a smaller project staying maintained.

Honorable mentions

  • Django ORM (standalone): usable without the rest of Django. If the ORM is what you love about Django, this is underrated.
  • Peewee: tiny, simple, sync-only. Great for small services, wrong for an async FastAPI push.
  • Prisma Client Python: nice DX on paper, but maintenance has been shaky — caution for anything long-lived.
  • Encode-style async ORMs (Ormar / others): Pydantic-friendly wrappers over SQLAlchemy Core; check maintenance status before committing.

3. Migrations (often the deciding factor)

Migrations, not query syntax, are where teams get burned.

ToolUsed byMaturityNotes

If long-term schema evolution scares you (it should), that alone pushes toward the SQLAlchemy/SQLModel + Alembic camp.

5. Recommendation for this team

You're Django refugees eyeing FastAPI. Two honest paths:

1. Pragmatic / low-risk: FastAPI + SQLModel + Alembic + Postgres. Async and modern DX, an escape hatch to full SQLAlchemy, and the best migration tool in the ecosystem. This is the recommendation for most teams.
2. Django-comfort path: FastAPI + Tortoise ORM. The query API feels like the Django ORM you know, which shortens ramp-up — but budget for Aerich's rough edges and validate your migration workflow before you commit, not after.

Only reach for Piccolo if type-safety and its built-in admin genuinely move the needle and you're fine depending on a smaller project. And before any of this: be sure you actually need to leave Django — if the app is CRUD + admin, Django 5.x with async views may still be the cheaper answer.

Whatever you pick, decide the migration tool first — it's the thing you'll live with longest.
